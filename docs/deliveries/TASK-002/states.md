# 时间、状态与事务草案

主体规则沿用REQ-018/022–039/094–097；新增时间细节P01、补偿量化P03均待批准。场景D03–D14；契约C02–C08。

## P01 时间与激活完整提案

业务时区Asia/Shanghai，服务端存UTC毫秒整数并输出带offset的RFC3339毫秒串；区间统一[start,end)，end时刻不可再消费。退款用整数毫秒差，比例有理数计算后一次四舍五入到分，不用浮点。自然日/日历月先在业务时区运算再转UTC，不能把所有月换30天。历史政策保存zone、calendarRule、precision、版本，未来时区变更不追改已售快照。

卡建议首次成功入场原子激活；购买时不消耗期限，是否设置激活截止日期待批准，不私设无限期承诺。私教期限商品建议首次履约激活；个人订阅建议支付确认即激活，期限价格仍Q06。卡销售前展示激活基准。日卡建议覆盖激活所在自然日，2026-11-11 23:50激活，end为11-12 00:00，只有10分钟；必须显著提示，也可选“次日同刻24小时”分支，但两者都未批准，不能暗用24小时。

月/季/年卡建议从激活当地时刻加1/3/12个日历月，目标月无该日则钳制到月末同刻，每次按原锚点推算而不逐月漂移。2026-01-31 10:00月卡至02-28 10:00；季卡至04-30 10:00；2024-02-29 10:00年卡至2025-02-28 10:00（历史夹具）；有效期终点不含。赠送期限若以天售卖须显式自然日/时长单位，提案为日历天同刻加算，不混称日卡。次卡次数与截止期限双门槛，入场状态独立。

门店服务到期E，正常t<E，宽限[E,E+15日历天)，停用t>=E+15日历天。E=2026-11-11 00:00则11-26 00:00停用，11-25 23:59:59.999仍宽限。30天提醒建议E-30日历天同刻创建一次站内提醒，续期版本变更重新排程；幂等键store+termVersion+reminderType。任务延迟后补发但标实际发送时间，不谎称准时。E相同则提醒10-12 00:00。

退款7自然日建议申请当日不计入，deadline为申请当地日期+8天的00:00（第7天结束）；11-11 23:50申请，须11-18日结束前审核并发起，11-19 00:00超时可升级。可选“申请日计第1天”会提前一天，待批准；发起不等到账，渠道时限另待Q08。

锁等待超时返回可重试冲突，不能返回业务成功；同幂等键同请求返原结果，异体409。调用外部渠道不持数据库锁；先事务记意图，再发送，再事务记结果；超时查询原渠道单，不生成第二资金指令。Outbox失败重试与Inbox去重，重放不能重复发卡/退款。

## P03 退款与补偿例题（待批准组合量化）

统一公式不变：期限实付×剩余有效时长/购买总有效时长，次数实付×剩余次数/总次数；赠送计总权益；累计实退<=实付，舍入到分，不扣手续费。建议将补偿视为返还原本损失的可用时间，不扩购买分母；分子用未消耗有效时长含尚未兑现的停用损失，不把日历经过等同消费。替代方案为分母增加补偿时长，但会稀释退款比例，须协调者明确，禁止两种口径混用。

例A：购买20赠10，共30时长单位，实付100元，已正常可用20，停用损失5，恢复后剩5+补5=10；建议分母30，退33.33元；若分母35则28.57元，为未推荐待决定分支。例B：原可用[0,15)，停用[10,20)，t=18尚未恢复申请；已可用10，损失[10,15)为5，按建议余额5/15、实付150元退50元；不能因日历到期退0。快照只计至申请时点已发生交集，未来损失不预支；退款成功不再发补偿。

例C：S04夹具[0,15)停[10,20)恢复20，损失5接到25；原到期30则补10到40。重复恢复补0。例D：停用[10,20)，退款hold[12,18)，损失归并为[10,20)，不是10+6；驳回补时不能再补该6。恢复时扣已补区间，后来停用只按新的原可用交集，账本保存区间来源，不能用当前endAt重扫旧区间。

例E：100元买10赠2次，共12次，耗3退75元；有期限次卡仍剩9次但截止已过，建议继续按9/12退款而不能消费（期限是消费门槛，不静默把余额清零），须P03批准；次数耗尽但期限仍长，次数公式退0，不转换期限退款。无期限次卡不补时间，有期限次卡只延期限不赠次。例F：0.01元总2剩1，舍入退0.01元；重放成功不再次支付。

账本建议：GrantLedger记录购买/赠送基数；UsageLedger记录真实消费；LossInterval记录停用或hold损失；CompensationLedger记录已归并返还区间；RefundSnapshot记录分子分母、实付、累计退款、policyVersion、权益版本和损失引用；MoneyLedger唯一退款资金指令记实退。相同损失区间只能分配一次，hold与停用取并集；退款成功关闭剩余和待补偿claim，驳回/撤回释放hold并补回实际损失，真实消费不回滚。分段区间排他约束/锁内归并仍需实现验证，不声称靠唯一字符串键足以排除所有重叠。

## 退款暂停状态补充

按P02/P03批准后的适用资格，PENDING_ACTIVATION、EXPIRED（仍有可退余额）也可进入REFUND_HOLD；快照保存previousStatus、activationAnchor、heldRemainingDuration及remainingUnits。驳回/撤回不一律改ACTIVE：未激活返回PENDING_ACTIVATION且不因审核自动激活；到期卡按可返还损失重新推导状态，无可返还可用时长仍EXPIRED；耗尽次卡不因补期限变得有次数。ACTIVE卡也须结合恢复后时间/次数/门店服务重新派生能力。状态与“有余额可申请退款”分离，退款资格不等同消费资格。适用日卡及到期次卡政策仍待P02/P03批准。

## REV-002-01：唯一首入场事务与可达状态

P01仍待批准。按本稿推荐的FIRST_ENTRY政策，用户只调用C04 EnterStore；删除C03公开独立activate路径，不给实现者二选一。C03内部ActivateForEntry只能由C04服务scope调用并加入同一事务，禁止单独提交。显式ACTIVATE_ONLY不是本稿开放命令（422 POLICY_UNAPPROVED），若以后批准其他激活基准须另升级政策与契约。

首入场资格与一般已激活消费资格分开：账号有效、用户本人或具本店代登权限前台；卡属于subject且store一致、订单已确认发放、status=PENDING_ACTIVATION、无退款hold/关闭、有足够次数（若次数型）、在已批准激活窗口内、服务正常或宽限；未批准激活政策不推算默认期限。待激活卡仅获“尝试首次入场”的局部资格，不因此提前获得公共付费能力。已激活卡才走现有有效期/次数检查。

事务顺序：取得Account栅栏→门店服务→相关order→entitlement锁，复核账号、服务、归属、hold及版本；查幂等回执，再核验并锁一次性challenge（绑定subject/store/expiry）；分配visitId，以同一serverNow计算start/end，C03设置激活；若本卡入场计次则C03以visitId消费键扣1；Visit所有者创建IN记录；写挑战已消费、幂等回执及事件Outbox，最后统一提交。任意步骤失败全回滚，包括激活时间、次数、Visit、挑战使用标记及回执；事务外不能先宣称激活成功。前台manualReason也走同一事务，记录代登actor。

约束：同账号同店至多一个未离场Visit；并发首入场串行，一次激活/扣次/Visit。相同幂等键返原回执；另一键复用挑战409 CHALLENGE_REPLAY；新挑战但已IN返409 ALREADY_IN且不再激活扣次。跨店404且不消费挑战，合法端重试仍可用；已退款hold、服务停用或扣次失败均不残留半激活。退场不回滚真实入场消费。

FIRST_ENTRY下“已激活且从未成功入场/消费”的日卡组合不可达，P02激活未用分支明确不适用，不为了凑分支添加独立激活。已成功入场即为本稿P02的“已用”（政策提案），即使尚未达到榜单有效日阈值；服务异常可在未激活或已用任一状态进入人工渠道。若未来批准显式激活政策，“激活未用”才可达并按P02待批比例分支处理。FIRST_FULFILLMENT私教仅由C08首次完成履约原子激活及消费，无Visit；PAYMENT_CONFIRMED个人订阅在发放时激活、没有入场语义。三类activationPolicy必须保存商品快照，不能相互替代。

## REV-002-02：账号关闭与清理的先后边界

Account状态ACTIVE→CLOSED，CLOSED不可回到ACTIVE；确认准备只是短期closureToken，不改变状态，不算已注销。TASK-003 CloseAccount为唯一用例：先展示卡/员工身份/未结交易影响和保留说明，要求本人有效会话、近期重新验证及二次确认；确认事务内锁Account，复核token绑定accountId/sessionEpoch/impactVersion及expiry。新出现的未结交易导致impactVersion不同则409 IMPACT_CHANGED、重新展示，不静默改变经济权益。

同一本地事务由身份模块设置CLOSED、closedAt、sessionEpoch+1、撤销会话/刷新令牌链；调用健康所有者RevokeAllConsents更新授权epoch、身份关闭栅栏阻止全部新访问；创建closureId、各模块清理Outbox及审计。任一步（含健康同步撤授权）失败全部回滚，不返回确认成功。事务提交是不可逆确认点，响应仅含closureId/accountStatus=CLOSED/cleanupState=PENDING，不发新账号会话。响应丢失可用关闭前绑定的幂等操作凭证取同一最小回执，该凭证不能读资料或登录。

新登录、OAuth绑定/静默登录、刷新和所有端每次访问均读取Account状态，CLOSED统一拒绝（旧凭证401 SESSION_INVALID；已验证凭据的新登录403 ACCOUNT_CLOSED，对未验证身份仍用通用认证失败防枚举）。不得按相同手机号/第三方subject自动重建旧Account。账号关闭和授权撤回同步提交，不能等异步健康清理才生效；异步清理失败cleanupState=RETRYING/NEEDS_ATTENTION，Account仍CLOSED，重试不能恢复账号。清理完成可标DONE，不删除用于拒绝旧登录的最小关闭标识；标识具体保留方式/期限仍P08上线核查。

跨模块并发统一先取Account栅栏，再取业务锁（服务→order→权益→refund/授权等子集），健康读取/导出在响应交付或导出链接发放前重新进入同一栅栏复核。若读取先完成交付则发生在关闭前，已经送达不能追回；关闭先提交则不得交付。旧导出链接也经鉴权下载而非长期裸URL。清理作业和回调用限定内部服务主体，不借用户会话；关闭后原退款仍可对账/审核/原路退款，不因关闭自动撤回、成功或改金额；与申请并发，申请先提交则纳入关闭影响，关闭先提交则用户申请拒绝。经济处理与数据最小保留分离。

注销有未结交易时不自动免债、赠退或没收卡余额。具体确认准入及注销后客服代理核验、员工交接和权益处置细则为P08/P07待批准提案，未批准不得上线该分支，但不得恢复已确认关闭的账号来处理旧交易。未来是否允许同标识重新注册也待P08；若批准必须新accountId、全新授权/健康空间，不恢复CLOSED旧账号或旧健康资料。

## REV-002-03：退款失败、未知及人工闭环

以下规范化状态替代原退款行的简化表达，金额与申请快照不变。REQUESTED可拒绝/撤回并恢复派生权益；审批后用户不能自行撤回。

| 状态 | 含义及允许转换 | hold/执行者 |
| --- | --- | --- |
| APPROVED_NOT_SENT | 已批准，明确未发渠道；发送前本地失败仍此状态并记attempt错误；发送工作者CAS取得发送权→SUBMITTING | 保持；TASK-005重试原instructionId，不重新申请 |
| SUBMITTING | 已记发送意图，可能已对外发送 | 保持；肯定受理→PROCESSING，明确失败→FAILED_CONFIRMED，无法确定→UNKNOWN |
| PROCESSING | 渠道明确受理且处理中 | 保持；查询/可信回调→SUCCEEDED或FAILED_CONFIRMED；失去可靠结果→UNKNOWN |
| FAILED_CONFIRMED | 渠道明确本次失败，不等于整个指令永不可能成功 | 保持；retryable且适配器支持原ID安全重试→SUBMITTING；不可重试/长期失败→MANUAL_REVIEW |
| UNKNOWN | 网络超时/丢响应等，不可推断未提交 | 保持；只查询/对账原ID，可确定后转对应状态；长期未知→MANUAL_REVIEW，不盲发新指令 |
| MANUAL_REVIEW | 人工接管；同时保存lastChannelState和证据，不覆盖未知事实 | 保持；有退款处理专权者可发起查询、允许的原ID重试，可信成功→SUCCEEDED；不能手工写“资金成功”或另做线下退款 |
| SUCCEEDED | 匹配原指令的可信资金成功已确认 | 同事务唯一资金入账、关闭对应权益；失败/处理中迟到通知不降级，仅留审计；重复成功无副作用 |
| ABORTED_UNSENT | 仅明确从未对外发送、全部发送任务已栅栏撤销的终态，政策P07待批准 | 平台refundResolve专权+复核者批准，锁内取消意图后调用权益恢复/去重补时；不能用于曾SUBMITTING的指令 |

审批时生成一次instructionId（refundId+mode唯一）、不可变amount/currency/beneficiary/snapshotHash。attemptId可每次变化但资金instructionId不变；适配器不支持同ID幂等重试则只查询并转人工，不自行换ID。重试前查累计实退和指令状态，禁止SUCCEEDED重发；FAILED_CONFIRMED的retryable由适配器已验证语义判定，真实码未接入时只能标未知能力、禁止真实重试。

发送与人工放弃竞争：工作者在同一退款锁内由APPROVED_NOT_SENT领取发送权、递增dispatchEpoch并提交SUBMITTING后才可发送；人工ABORTED_UNSENT只允许从未领取过发送权、无外发记录并取消全部Outbox的指令，epoch使未领取旧任务失效。只要曾领取发送权即视为可能发送，不能凭本地“没看到响应”恢复权益。审批后明确渠道失败、长期失败或未知均不自动恢复、不新建同单退款，继续保留hold并展示升级入口；若要支持“曾发指令最终失败后恢复”，须另经P07批准及渠道证明不可再付款的终结/撤销协议，当前草案不开放该操作。

人工操作、查询结果及回调均以order→entitlement→refund锁和version串行（需要用户Account栅栏的业务命令先取栅栏；内部回调仅内部scope，不恢复关闭账号）。可信迟到成功从SUBMITTING/PROCESSING/FAILED_CONFIRMED/UNKNOWN/MANUAL_REVIEW收敛SUCCEEDED，关闭权益、写唯一MoneyLedger；人工先记录接管/重试也不释放hold，故不会同时消费。成功先到则人工重试409 REFUND_ALREADY_SUCCEEDED。校验不符回调隔离，不更新资金与权益；ABORTED_UNSENT收到所谓成功属于“从未发送”证明被破坏的严重异常，立即隔离及封锁相关权益消费、对账告警，不能静默吞通知或宣称跨渠道安全已证实。该前提须实现阶段故障注入验证，本轮不开放真实渠道。

用户呈现：未发送=“已批准，待发起/发起前重试”；明确失败=“退款发起失败，处理中/已升级”，unknown=“结果确认中，请勿重复申请”；人工=“人工核查中”；成功同时区分资金确认/到账字段，不承诺固定到账日。失败持有时长和人工服务SLA待P07批准，长期失败必须升级，不能悄然让任务消失；自动重试次数/退避由实现契约另定，均不改变申请金额。该安全优先的hold策略与审批后放弃权限是设计提案，未冒充已批准商业政策。
