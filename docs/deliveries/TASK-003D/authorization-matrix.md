# 授权矩阵与纸面反例

仅设计待验收，没有运行权限测试。依据[权限](../TASK-002/permissions.md)、[D01/D02/D16/D25](../TASK-002/scenarios.md)；接口S01–S09见[会话契约](session-contracts.md)。REQ-002/006/013/014/015/085/093/097。模型唯一所有权见[模型](identity-model.md)。

## 判定顺序与矩阵

拒绝优先：R1当前Account/Session epoch有效→R2服务端主体及资源所有者相符→R3当前员工role与merchant/storeScope及操作许可→R4实际会员来源及门店服务状态→R5健康consent→R6关闭栅栏。只执行操作涉及的判定：员工操作无需会员，健康手动/本人历史无需付费。未知/依赖失败不放行；客户端entry仅入口过滤，不能从字符串得到角色。跨归属404，未认证401，同归属无能力403；查询与写入/响应交付都复核，不能先查所有租户再前端过滤。P04细分操作未批则422 POLICY_UNAPPROVED，不当作允许。

| 规则 | 主体/role与范围 | 资源/会员来源 | 允许 | 拒绝及反例 |
| --- | --- | --- | --- | --- |
| R1 | 任意用户及员工，所有入口 | Account ACTIVE、有效Session与当前epoch | 进入后续判定；会员到期仍可认证 | CLOSED、过期或撤会话401；已验证新登录CLOSED为403；I09/I10/I11/I12/I15/I16 |
| R2 | 用户本人/服务端确认所有者 | 本人账号、历史卡、手动健康；不要求会员 | 本人历史、免费记录 | 他人资源或伪造subject/entry拒绝；I01/I02/I07 |
| R3 | OWNER、MANAGER、FRONT_DESK、COACH分别授予；PlatformGrant另判 | merchant必须匹配资源真实merchant，store须在当前scope | 已确认必要员工操作；具体permission按批准清单；到期会员不影响有效员工 | 同商家也不能越scope；撤授/过期即时拒；店主无自动平台权；P04授予细节未批；I01/I03/I04/I05/I06/I08 |
| R4 | 本人会员，无员工role要求 | C03返回PERSONAL或STORE来源；来源可独立叠加 | 任一有效来源授公共付费，店专属仅本店有效卡且服务可用 | 个人卡不给店专属；员工不给AI；一店停用不撤他店/个人；到期本人历史仍可；I02/I06/I07/I14 |
| R5 | 教练有效授予+本人教练关系；管理员/客服无豁免 | 资料owner=学员；由TASK-006核对coach/category/expiry/epoch | TASK-006最终裁决有效明确授权类别与期限，付费不是健康读取授权替代 | 无授权、撤回、超类别/期限拒绝；预约/本店/客服身份不等于健康同意；I04/I05/I08/I12 |
| R6 | 关闭本人及限定内部服务主体分开 | CLOSED与cleanup不同维度；未结资金仍归交易模块 | S09最小原回执；内部原退款对账按限定scope继续 | 关闭后旧Session/refresh/新登录/旧导出拒；清理失败不恢复；回执不能读资料；I10/I11/I12/I13/I16 |

主体、资源归属、有效role、门店scope、会员来源及健康consent分别取当前所有者事实；其中任何必要维度未知都不能用另一个维度补足。不创建统一“会员员工超级角色”。商家服务宽限的既定禁新增收费规则继续生效；P04必要操作细化未经批准不可扩大。
